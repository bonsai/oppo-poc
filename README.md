# 声の掲示板

> **悩みを一本の声にして放出し、誰かの声に答えることで、自分も少し軽くなる。**

このプロダクトは、声を大量に消費するSNSではない。
一日一本、自分の声を放出し、少数の匿名の声と出会い、そのどれかに答える。

**減らすことで、出会いを増やす。**

## MVPで作るもの

MVPの目的は「機能をたくさん作ること」ではなく、次の循環が本当に成立することを証明すること。

```text
今日の声を一本吹き込む
        ↓
Safety判定
        ↓
少数の匿名の声が届く
        ↓
どれか一つを聴く
        ↓
声で答える / 流す
        ↓
自分の悩みも放出できる
        ↓
次の日へ
```

### 必須

- 匿名で声を一本吹き込む
- 一日一回の投稿制限
- STTによる内容取得
- 配信前のSafety判定
- `ALLOW / HOLD / REJECT`
- 少数の匿名Voiceを受け取る
- Voiceを聴く
- Voiceを選んで声で返答する
- 返答を安全判定してから届ける
- 自分の投稿と受け取った声を秘匿する
- 返答したことで、自分の声も放出できる体験

### 弾力的にするもの

受信数は「3件固定」にはしない。

```yaml
inbox:
  limited: true
  adaptive: true
```

具体的な件数や配信ロジックはSettingsとして後から調整できるものとする。
MVPでは「大量ではなく、少数の声が届く」ことだけを保証する。

## MVPで作らないもの

MVPでは、以下を意図的に作らない。

### SNS機能

- フォロー
- フォロワー
- いいね
- リポスト
- 公開プロフィール
- 公開ランキング
- フォローフィード
- 数字を競う仕組み

### 無限コミュニケーション

- 無制限チャット
- 無制限のAIチャット
- DM機能
- 常時接続型の会話
- 無限スクロール
- 過去ログを際限なく掘るUI

### 探索機能の作り込み

- 高度な検索
- タグ検索を中心とした体験
- Roomを中心としたコミュニティ構造
- 完璧なレコメンド
- 完全一致する相談相手探し

偶然の出会いを残すため、MVPでは「自分で相手を探す」ことを主目的にしない。

### プロフィール・権威化

- 詳細プロフィール
- フォロワー数
- 専門家ランキング
- 資格による権威付け
- 実名公開

得意分野は将来的な配信判断のための設定として扱えるが、MVPでは公開プロフィールにしない。

### AI住民の作り込み

AIは参加できる設計余地を残すが、MVPではAIを無制限に投稿させない。
AI参加は人間と同じ制約の中に置く。

### 過剰なDomain

MVPでは以下を最小限の概念として扱う。

```text
Participant
Voice
Reply
Delivery
SafetyDecision
```

`Wish / Proof / Room / Tag` など既存設計の概念は、Core Loopに必要になるまで実装しない。

## 安全性

安全性は後付け機能ではなくMVPの境界そのもの。

```text
Voice
  ↓
STT / 音声信号
  ↓
Moderation Application Service
  ↓
Safety Agent
  ↓
ALLOW / HOLD / REJECT
  ↓
Delivery
```

- `ALLOW` → 配信可能
- `HOLD` → 保留・再評価
- `REJECT` → 配信しない
- 悪意が継続する場合は将来Shadow Modeへ接続できる境界を残す

Safety Agentだけに安全性を丸投げせず、最終的な配信可否はApplication / Domain Policyで決める。

## 秘匿性

**公開しない。匿名化するだけでもない。秘匿化する。**

- 生音声を公開URLで配信しない
- Voiceは認可された経路からのみ取得する
- 音声・文字起こし・派生データを同じ秘密境界で扱う
- 不要な個人識別情報を保存しない
- 削除時は関連データも削除対象にする

## Agent境界

通常の会話AgentとSafety Agentは分離する。

```text
Hono / TypeScript
       ↓
Application Service
   ┌───┴────┐
   ↓        ↓
Normal   Safety
Agent     Agent
             ↓
       Safety Decision
```

MastraはApplication境界の内側で利用し、Domainそのものにはしない。

## 実装境界

MVPの基本技術は以下。

- Hono
- TypeScript
- R2：音声などの秘匿データ
- D1：最小限のメタデータ
- STT：Voiceの内容取得
- Mastra：Agent / Safety Agentの実装境界

ただし、技術を増やすことをMVPの成果にしない。

## 作る / 作らないの判断原則

機能追加を迷ったら、次で判断する。

> **「今日一本吹き込み、少数の声を受け取り、どれかに答える」というCore Loopに必要か？**

必要でなければMVPには入れない。

さらに、

> **その機能が「減らすことで、出会いを増やす」という思想を弱めるなら作らない。**

## 技術原則

- HonoをWeb/APIの入口にする
- TypeScriptで統一する
- FEはAPIを境界として利用する
- 音声中心で、GUIを主役にしない
- MastraをDomainそのものにしない
- DDDは境界と言葉を揃えるためだけに使う
- 小さく作り、E2Eで体験を固定する
